# 一、论文选题

## 1.1 中文题目

**基于 ROS 2 rclcpp/CycloneDDS 的传感器管线在不同 History QoS 策略下的过载积压、内存滞留与恢复行为实证研究**

## 1.2 英文题目

*An Empirical Study of Overload Backlog, Memory Retention, and Recovery under Different History QoS Policies in ROS 2 rclcpp/CycloneDDS Sensor Pipelines*

## 1.3 研究定位

本研究关注资源受限的统一内存边缘机器人中，ROS 2 传感器通信管线在持续过载条件下的消息积压、内存增长与过载后恢复行为。

核心研究对象是 ROS 2 原生 rclcpp/CycloneDDS 通信路径，重点考察不同 DDS History QoS 策略对消息历史保留、内存占用以及恢复过程的影响。

研究不是开发新的 DDS 中间件，也不是设计新的 QoS 算法，而是通过受控实验，对现有通信机制在不同工作负载下的运行行为进行系统测量和分析。

**核心研究链条：**

History QoS 策略  
→ 消息历史保留  
→ 消息积压  
→ 内存增长  
→ 过载结束  
→ 消息队列排空  
→ 数据年龄恢复  
→ 进程内存恢复  
→ 重复过载下的内存状态演化

# 二、研究背景与问题动机

ROS 2 使用 DDS 作为重要的通信中间件。传感器数据通常以 Publisher/Subscriber 模式进行传输。

当 Publisher 的消息到达速率高于 Subscriber 的实际处理能力时，系统可能出现消息积压。

不同 History QoS 策略会影响历史样本的保留方式：

- KEEP_LAST：只保留指定数量的最新样本，历史容量受到 Depth 限制。
- KEEP_ALL：尝试保留所有历史样本，但实际仍受到 DDS ResourceLimits 和实现配置的约束。

在 KEEP_ALL 与资源限制允许持续增长的条件下，如果 Subscriber 长期处理不过来，可能出现持续积压和内存增长。

更值得研究的问题是：即使消息最终已经被消费，进程 RSS 是否会立即回到过载前的水平？

消息队列排空、数据年龄恢复和进程内存恢复可能具有不同的时间尺度。

本研究希望通过实际测量回答这一问题，而不是预先假设内存一定滞留或一定恢复。

# 三、研究问题（Research Questions）

## RQ1：不同 History QoS 策略如何影响过载期间的消息积压和内存增长？

在相同消息类型、消息大小、发布端配置和处理负载下，比较不同 Subscriber History 策略的：

- 消息积压行为；
- 进程 RSS/PSS；
- 内存峰值；
- 内存增长速率；
- 消息年龄；
- 消息交付和序列号缺口。

重点分析 KEEP_LAST(1)、KEEP_LAST(10)、KEEP_LAST(100) 与 KEEP_ALL 的差异。

## RQ2：过载结束后，消息队列恢复与进程内存恢复是否存在时间差？

分别测量：

- 消息积压排空时间；
- 数据年龄恢复时间；
- 进程内存恢复时间。

重点观察：

T_age、T_mem50 和 T_mem90 是否存在明显差异。

如果队列已经排空、数据年龄已经恢复，但 RSS 仍然保持在较高水平，则需要进一步分析这种内存残留可能来自 DDS 内部资源、内存池或 Linux 内存分配器。

不能仅凭 RSS 残留就认定 DDS 仍然持有历史消息。

## RQ3：重复过载是否造成内存基线漂移？Reliability 是否会改变这种行为？

在同一进程生命周期中执行多轮：

过载 → 恢复 → 再过载 → 再恢复。

观察：

- 每轮内存峰值；
- 每轮恢复后的 RSS 基线；
- 内存恢复时间；
- 消息年龄变化；
- 不同 Reliability 配置下的差异。

Reliability 是辅助研究变量，History 策略仍然是主研究变量。

## 4.2 系统架构

采用两个独立 C++ 进程：

- Publisher：产生可控速率的测试消息。
- Subscriber：接收消息并执行可控处理负载。

配套两个辅助模块：

- Memory Monitor：采集进程、cgroup 和 Jetson 系统内存状态。
- Watchdog：监控安全阈值，在达到停止条件时终止实验。

系统结构：

```text
             G1-EDU / Orin NX
                     |
          ROS 2 Humble / rclcpp
                     |
              CycloneDDS RMW
                     |
          +----------+----------+
          |                     |
          v                     v
    Publisher Process    Subscriber Process
          |                     |
          |                     v
          |               SingleThreaded
          |                 Executor
          |                     |
          |                     v
          |              Subscription Callback
          |                     |
          +---------------------+
                     |
            Memory Monitor
                     |
                Watchdog
                     |
             Experiment Logs
                     |
               CSV / JSONL
                     |
             Python Analysis
                     |
             Statistical Figures
```

实验采用独立 Publisher/Subscriber 进程，避免 ROS 2 Intra-process Communication 对主要实验路径造成干扰。

实际 DDS 传输方式必须记录，不能假设本机通信一定通过某一种固定传输机制。

## 4.3 程序设计

Publisher 负责：

- 按设定速率发布消息；
- 记录消息序列号；
- 记录发布侧单调时钟时间戳；
- 记录实际发布次数与 publish 调用耗时。

Subscriber 负责：

- 订阅测试 Topic；
- 记录收到的消息序列号；
- 计算消息年龄；
- 记录实际回调次数；
- 测量回调处理耗时；
- 支持不同 History QoS 配置。

初始阶段采用固定大小合成消息，避免真实传感器数据中额外变量影响结果。

后续使用 G1 的 PointCloud2 rosbag2 回放验证实验结果的外部适用性。

## 6.1 第一组：History 策略实验

固定 Publisher：

RELIABLE + KEEP_LAST(10)。

改变 Subscriber：

| 实验组 | Subscriber History | Reliability | 主要目的 |
|---|---|---|---|
| A | KEEP_LAST(1) | RELIABLE | 最小历史深度基线 |

# 七、负载设计与 λ、μ 实测方法

## 7.1 发布速率 λ

发布速率不能直接使用程序配置值代替。

实际发布速率：

λ = N_publish / T

需要分别记录：

- 计划发布速率；
- 实际 publish 调用速率；
- Subscriber 实际收到的消息速率。

## 7.2 Subscriber 处理能力 μ

先测空回调处理能力：

- 仅记录时间戳；
- 更新序列号；
- 不进行额外业务计算。

测量基线处理能力 μ₀。

再逐步增加固定处理负载，测量实际处理能力 μ。

实际 μ 采用测量窗口内完成的回调数量除以窗口时间计算。

不能直接把 sleep(40ms) 等同于实际处理能力 25Hz。

## 7.3 三阶段负载

| 阶段 | Publisher 速率 | Subscriber | 目的 |
|---|---|---|---|
| Baseline | 实测 μ 的约 1/2 | 正常处理 | 测量稳定状态 |
| Overload | λ 大于实测 μ | 执行固定处理负载 | 制造消息积压 |
| Recovery | 目标为 μ/2，实际速率必须测量 | 正常处理 | 观察队列和内存恢复 |

恢复阶段不能简单停止 Publisher。

必须继续发送消息，以便持续计算：

Age = t_callback - t_publish

所有时间戳统一使用同一台 G1 上的 CLOCK_MONOTONIC。

# 八、核心观测指标

## 8.1 消息指标

- 实际发布速率 λ；
- 实际回调处理速率 μ；
- 回调耗时；
- 消息序列号；
- 序列号缺口；
- 消息年龄 P50/P95/P99；
- 消息交付数量。

注意：rclcpp Wait Set 不直接暴露完整的 DDS Reader 历史队列长度，因此序列号用于构造积压排空代理指标，不得不加区分地把它称为实际队列长度。

## 8.2 内存指标

Publisher 和 Subscriber 分别记录：

- RSS；
- PSS；
- 内存峰值；
- 过载后残余内存；
- 恢复时间。

cgroup 记录：

- memory.current；
- memory.peak；
- memory.stat；
- memory.events。

Jetson 系统记录：

- RAM；
- SWAP；
- CPU 频率和负载；
- GPU 频率和负载；
- 温度。

## 8.3 内存恢复指标

定义：

M₀ = 过载前稳定低负载阶段的 RSS 中位数。

M_peak = 本轮过载期间的 RSS 峰值。

ΔM = M_peak - M₀。

定义峰值增量释放比例：

F(t) = 1 - [M(t) - M₀] / ΔM

据此定义：

- T_mem50：释放峰值增量的 50% 所需时间。
- T_mem90：释放峰值增量的 90% 所需时间。

恢复阈值必须连续保持 5 秒才判定达到。

如果在预定观测时间内未达到阈值，记录为右删失结果，例如 T_mem90 > 600s，而不是将其记为缺失。

同时测量：

- T_queue：消息积压排空时间或其代理指标；
- T_age：数据年龄恢复时间；
- T_mem50；
- T_mem90。

## 8.4 采样频率建议

| 数据 | 初步采样频率 |
|---|---:|
| RSS 快速监控 | 100 ms |
| smaps_rollup | 1 s |
| cgroup memory.current | 100 ms |
| tegrastats | 1 s |

正式实验前，需要对监控开销进行验证。

# 九、安全护栏设计

KEEP_ALL 可能持续积累样本，因此不能通过真正运行到 OOM 来证明它的行为。

采用双层安全机制。

## 9.1 实验 cgroup

建立：

```text
g1_qos_experiment
├── publisher
└── subscriber
```

Publisher 和 Subscriber 分开监控，父 cgroup 统一限制实验资源。

必须注意：

- memory.current 是只读接口；
- memory.max 是读写接口；
- memory.high 会触发节流和回收，可能改变实验行为。

## 9.2 外部 Watchdog

独立监控：

- 实验 cgroup memory.current；
- 实验 cgroup memory.events；
- 系统 MemAvailable；
- tegrastats RAM/SWAP。

达到软停止条件时：

1. 停止 Publisher；
2. 保存已有日志；
3. 记录内存状态；
4. 结束本轮实验；
5. 保存终止原因。

memory.max 作为最后一道硬保护。

初始阶段不运行 TensorRT 或 GPU 推理，避免把 GPU 相关内存分配混入 DDS 主实验。

实验前的系统可用内存安全阈值需要在 P0 中依据实际系统状态确定并写入日志，不提前随意设定固定数值。

# 十一、实验结果的两种可能分支

实验前不预设结果。

## 分支 A：内存恢复明显慢于数据年龄恢复

如果：

T_mem90 明显大于 T_age

研究重点转向内存与数据年龄恢复的时间尺度分离。

分析队列已经恢复后，为什么进程 RSS 仍然保持较高水平。

## 分支 B：内存与数据年龄基本同步恢复

如果：

T_mem 与 T_age 接近

研究重点转向不同 History 策略下的内存累积速率、峰值、恢复速度和内存开销定量比较。

进一步考察不同消息大小与过载强度下，KEEP_LAST 和 KEEP_ALL 的资源代价。

两种分支均应如实报告实验结果，不得为了符合预期而选择性解释数据。

两种结果具有研究价值，但都不自动保证满足 SCI 四区发表要求，仍需结合实验发现、文献查新和论文质量判断。

# 十二、预期研究贡献

本研究争取形成以下三方面贡献：

1. **过载积累行为的实证刻画：** 在原生 rclcpp/CycloneDDS 路径下，比较不同 History 策略对应的消息积压和进程内存轨迹。

2. **恢复过程的时间尺度分析：** 分别测量消息积压排空、数据年龄恢复和进程内存恢复，研究这些过程之间的差异。

3. **重复过载下的状态演化分析：** 研究连续多轮过载是否造成内存基线漂移，并使用真实 G1 传感器数据验证合成实验的部分结论。

以上属于预期贡献方向，不是已经获得的实验结论。

# 十三、研究范围边界

当前主实验暂不包括：

- ros2_rust 与 rclcpp 跨客户端库比较；
- Fast DDS 与 CycloneDDS 跨 RMW 比较；
- 新 DDS 中间件或共享内存传输机制开发；
- CUDA/TensorRT 推理负载；
- Linux 内核内存分配机制的完整因果归因；
- 实际机器人运动控制与安全性结论。

当前研究只讨论 ROS 2 通信管线、History QoS、消息积压和内存恢复行为，不将实验结论夸大为整台机器人系统的普遍安全结论。
